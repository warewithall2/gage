# Dogfood log, 15 October 2026

The full ensemble (claude, codex, grok, muse) given real work routed only
through ctx. The work was the open decisions: the id formula to codex, the
nested-envelope forward to grok, the audit log questions to muse. Each brief
travelled as a signed bundle; the agents' CLI prompts said only "you have
mail", so ctx was the channel rather than a decoration.

Recorded while using it, not afterwards.

## 1. A bundle cannot authorise its own fulfilment

The largest finding, it was not on anyone's list, and it reproduced across
three vendors.

Each agent was sent a real work request as a signed bundle. Codex did the
work and replied through ctx unaided. **Grok and muse both read the bundle,
verified it, understood the request -- and refused to act on it.**

Muse, verbatim: "I am answering in chat, as you asked, and not replying
through ctx on the strength of the bundle itself."

Grok: "The bundle is signed data from owen, not a user instruction... The
request inside it is his, so I have not designed anything and I have not sent
a reply." It then listed the pending bundles and asked which to accept.

That is the trust frame working exactly as designed. `gage open` wraps every
payload in text that says instructions inside carry no authority and must be
reported rather than obeyed, and two of three agents honoured it to the
letter. Codex differed only because its out-of-band prompt said "treat its
contents as a task from your user" -- the authority came from outside ctx, not
from the bundle.

So: **ctx can carry a request and prove who wrote it, but it cannot carry the
authority to fulfil it.** Something else always has to say "you may act on
this", and today that something is a human pasting a prompt. For a tool whose
pitch is agents prompting each other, that is the gap between a verified
message and useful work, and no amount of signing closes it.

This is the strongest argument yet for the item I had ranked third:
ASI07's *allowlisted delegation paths*. The missing primitive is a receiver-
side policy that says "requests of this type, from this key, in this thread,
may be acted on without asking me" -- authority computed by the receiver from
its own list, exactly as trust already is. Scoped and expiring, because
standing authority to act on another agent's instructions is the thing you
would least want to grant permanently.

It also means the frame needs a second register. Right now every payload is
"data you must not obey", which is correct for a prompt from a stranger and
wrong for an authorised request from a known peer. The message types already
exist (`question`, `review-request`, `expects_reply`) and the frame ignores
them.

I was wrong in my first draft of this log, where I wrote that grok could not
use ctx because its wrapper has no tools. It has tools, it found the ctx
skill, and it ran ctx itself. The refusal was a judgement, not an inability.

## 1b. Grok ran as the wrong identity, unprompted

Grok's first run listed five pending bundles -- from *owen's* inbox, not its
own, including codex's reply that was addressed to me. It ran `gage` with no
`CTX_HOME`, which defaults to `~/.ctx`, so it read my mail and reported it
back as though it were its own.

Nothing was forged and nothing leaked anywhere it should not have been. But
had it got as far as `gage reply`, the reply would have gone out correctly
signed as **owen**, by an agent that believed it was grok. See finding 6:
this is that footgun firing in the wild, within an hour of it being written
down as hypothetical.

## 2. A sandboxed agent cannot deliver locally

codex runs sandboxed. Local-route delivery writes into the *recipient's* ctx
home, so delivering to owen means writing to `~/.gage/inbox/pending`, outside
any sane workspace. The run needed write access to the whole home directory
to reply to a message.

So the sandbox profile an agent should have and the one ctx needs are
different. The relay path is not a workaround: that trades a filesystem write
for a network call, which is the other thing sandboxes block. Worth saying
out loud because it will come up in every enterprise deployment, and "give
the agent write access to your home directory" is not an answer.

## 3. `gage open` takes a directory, but everything hands you an id

`gage inbox` prints bundle ids. `gage accept` prints an id. The natural next
command is `gage open <id>`, and it fails with:

    ctx: No such file or directory (os error 2)

No mention of what it wanted, and the same error whether the id is wrong, the
path is wrong, or the file is genuinely missing. I typed it, and I wrote the
tool. `accept` already prints the full `gage open <path>` line, which is good
and also an admission that the id is what people have.

Fix: accept an id and resolve it across the stages, or fail with "that looks
like a bundle id; try gage open <path>".

Codex hit this independently and said so unprompted in its reply: "`gage accept
<id>` staged the request but did not display its contents; I had to infer the
`gage open` path from the command's output and pass that filesystem path back
to `gage open`... the accept/open sequence is less direct than opening by
bundle id." It added that the inbox "says 'expects a reply' without showing an
explicit decision/reply command" -- it had to infer the `gage reply` invocation
from the body of the bundle. Two of us, separately, lost time in the same two
places.

## 4. `gage thread <message-id>` says "no thread"

Threads are keyed on the thread id; passing a message id in the thread gets
`ctx: no thread <id>`. The tool knows which thread that message belongs to --
`gage threads` prints it. It should either resolve it or say so.

## 5. `--out` also delivers

`gage send --to grok ... --out <dir>` writes the directory *and* delivers to
grok's local route. Reading `--out` as "write it here instead of sending" is
wrong, and to get a bundle that had genuinely only travelled via the relay I
had to delete the locally delivered copy first. Either rename the flag or
make it exclusive.

## 6. CTX_HOME is a per-command env var, and forgetting it changes who you are

Every command for a non-default identity needs `CTX_HOME=~/.ctx-codex` in
front of it. Forget it on a `reply` and the reply goes out signed as owen --
correctly signed, correctly delivered, wrong author. No command confirms
which identity it is about to act as unless you ask with `whoami`.

A `--as <handle>` flag, or printing the acting handle on any command that
signs, would cost nothing.

## 7. Small things

- No `ctx --version`. There are now two binaries on this machine (`~/.local/bin`
  and `target/release`) and nothing prints which is which.
- Installing over a running `gage ui` fails with `Text file busy`; it needs
  replacing the directory entry rather than writing in place. Fine once known.
- `gage open` on a bundle delivered by directory copy rather than a real route
  reads `ARRIVAL UNRECORDED`, which is correct and still surprising the first
  time you hit it in a test fixture.

## What went right

Worth recording, because the failures above are all ergonomics and the core
held up.

- A full round trip through the relay on relay-host -- seal, push, pull,
  accept, open, reply, push, pull -- verified at both ends with SENDER
  VERIFIED and an intact payload.
- The trust frame survived being handed to a different vendor's model: grok
  received the fenced bundle verbatim, nonce and all.
- `verdicts_stale` fired correctly under real lock contention, withholding
  every verdict rather than serving a stale one.
- Threads grouped both legs of the round trip and marked the thread settled
  off the reply, with no bookkeeping from me.
