Top finding: the hook can fire for a `share` grant that `ctx open` deliberately never prints as authorised, so its central “same authority the reader was shown” claim is false; announced/hook state is also conflated in a way that can both lose and duplicate hook runs.

## 1. `ctx watch --on-arrival`

> “The same lookup the frame prints, from the same inputs, so a hook can never fire on an authority the reader was not shown.” — [src/notify.rs](src/notify.rs:80)

False on two counts. It is a fresh snapshot, not the frame’s inputs: contacts and authority can change between poll and `open`, and grants are not rechecked before each hook in a batch executes. More concretely, `authority_block` is printed only for reply-expecting kinds, while the hook fires for `allow … share`; the frame intentionally says a share has nothing to authorise. So the reader was *not* shown that grant.

> “**The hook never receives the payload.**” — [README.md](README.md:553)

It receives the sender-written subject, and it receives `CTX_BUNDLE_ID`, which lets the hook run `ctx accept`/`ctx open` itself. “Not handed the items directly” is true; “never receives” as a containment claim is not. Likewise:

> “**It does not accept the bundle.** Afterwards the bundle is still unread, still in `pending`…” — [README.md](README.md:561)

That describes `watch`’s own code, not the post-hook state. Any hook can accept it.

On the environment: env delivery does keep sender text out of ctx’s `sh -c` string, and the `$(touch …)` test proves that narrow point. But —

> “**Sender-chosen text is data, never command.**” — [README.md](README.md:565)

is hook-dependent. Correctly quoted `"$CTX_SUBJECT"` is data; `eval`, a second constructed shell string, or unquoted expansion invites word-splitting, globbing, and option injection into the hook’s own commands. Env values are also inherited by children and inspectable via the process environment. The safe claim is “ctx does not interpolate it,” not that the channel makes it safe.

Mark-before-hook is the wrong failure direction for an *action*, as opposed to a notification. All ids are marked before any hook runs, so a crash, kill, timeout, or earlier long hook loses later hooks silently except on stderr. The code admits at-most-once, but even that is not guaranteed: `save_announced` says —

> “Keep it bounded; the oldest ids stop mattering once collected.” — [src/notify.rs](src/notify.rs:34)

`announced.json` is a `BTreeSet`, which has no arrival order; trimming keeps the lexicographically largest 2000 ids, not the newest. Corrupt or unwritable state also reloads as empty. The result can be both lost hooks *and* re-fired hooks. A separate hook-completed/retry state is not an optional refinement; one bit cannot represent “human notified” and “action done”.

## 2. Key-label note in `open`

The fix does block the exact case it now describes: a handle that is a live, retired, or group name in `contacts.json` still gets the loud warning. But the rendered note still asserts:

> “which is this key's own word-label and not a name anyone chose. You call it {nm}. Nothing is in conflict.” — [src/open.rs](src/open.rs:118)

A sender needs no grinding to suppress the warning: it sets its handle to its own label. Grinding (~65k tries) only becomes necessary to *choose which* pair. `is_a_name_you_use` checks contact names, retired names, and group names; it does not check labels of *other contact keys*, the receiver’s own handle, LAN/machine names, or case variants. An attacker can therefore grind a key whose label equals another key’s label — a 16-bit collision — and get “nothing is in conflict” for a string a reader may associate with that other key.

The result file also claims:

> “A handle the sender *typed* still gets the loud warning…” — [tests/injection/results/2026-10-16.md](tests/injection/results/2026-10-16.md:83)

The code cannot distinguish typed from derived; a typed handle equal to the label gets the note. And the two unit tests in [src/open.rs](src/open.rs:507) only assert `label != "mac"` / `label != "alice"`; they never call `render` or exercise `is_a_name_you_use`. The shell test covers more, but the unit tests do not “pin the distinction”.

## 3. Required `Origin` in the UI

Yes, there is a legitimate client this breaks, and it is conceded in the code: local scripts, helpers, and native apps that send `X-Ctx` without `Origin` now get 403. The answer that the CLI is the supported interface is a policy choice, not a demonstration of parity or of no supported API users.

The stated property is also too strong:

> “**the mutating routes are for this page only.**” — [src/ui.rs](src/ui.rs:215)

Any local process can send both `X-Ctx: 1` and the correct public `Origin`; there is no per-page secret. This stops cross-site browsers, which is worthwhile, but it does not make the routes page-only against local clients. The change is a compatibility narrowing dressed as a guard correctness fix. The page’s own fetch is unaffected, so no *browser* client I can see breaks; the break is non-browser local automation.

## 4. Email-shaped, not a board

The concessions in the text undo the headlines:

> “Something has to **host** it.” — [docs/thesis-and-plan.md](docs/thesis-and-plan.md:43)
> “**Sealing to one recipient breaks.**” — [docs/thesis-and-plan.md](docs/thesis-and-plan.md:48)
> “The **friend list stops being symmetric.**” — [docs/thesis-and-plan.md](docs/thesis-and-plan.md:53)

A relay already hosts sealed mail; a board could store sealed fan-out copies, use a group key, or be self-hosted. Sealing therefore does not “break”; it costs copies and rotation work. Symmetry is the weakest: contact lists in ctx are already local and pairwise-asymmetric — my listing you does not imply your listing me — so a board would not break a symmetry the current system has.

> “If a board is wanted later, that local view is the honest version of it.” — [docs/thesis-and-plan.md](docs/thesis-and-plan.md:59)

`ctx threads` is a local reconstruction from mail this machine happens to hold. It is not a shared board with shared membership, ordering, or visibility. Calling it “the honest version” substitutes a different product for the rejected one. The file admits the choice is “settled by preference”; the three reasons should be labelled costs and preferences, not rejection grounds.

## 5. Injection result calibration

The revised calibration is directionally right, but the file still over-credits causation:

> “Three things in the output did the work:” — [tests/injection/results/2026-10-16.md](tests/injection/results/2026-10-16.md:32)

Nothing isolates the nonce from the rest of the frame, the reader’s general training, this workspace’s standing bundle-handling instructions, or priming by having written the scaffold. There is no control run without the frame or with a weaker frame, no repeats, and no record sufficient to reproduce the reader’s context. The accidental name-mismatch warning is also described as:

> “but it is correct behaviour and it works.” — [tests/injection/results/2026-10-16.md](tests/injection/results/2026-10-16.md:46)

It was a false positive that happened to help; that does not show it “works” as a defence.

So the result is worth *less than the revised wording suggests if read as evidence about an unprimed reader*. It is a useful first case report that one primed reader, on one run, did not emit one secret tell. It is near-zero evidence about the population claim the thesis needs — that readers generally treat bundle contents as data — and it should not be used to justify either the renderer’s sufficiency or the new label-note behaviour.
