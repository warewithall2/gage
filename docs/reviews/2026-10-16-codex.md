## 1. `ctx watch --on-arrival`

> “It fires only where `Authority::lookup` already returns a grant.”

The code supports the narrower claim that the hook runs only when the lookup in `new_arrivals()` succeeds. But that lookup is a snapshot of local files and state, not proof that a human recently approved this action. The grant model is coarse, has no expiry, and the authority file can be changed by any process running as the user. The plan itself acknowledges that an agent with shell access can edit it. So “a grant already covers the message” is accurate about program flow; it can overstate the strength or freshness of the authorization.

> “The hook never receives the payload.”

It receives sender-controlled metadata, including the subject, through environment variables. That’s not the bundle’s file contents, but it is still message content. The environment is also not a general-purpose secret channel: the hook and its child processes can read it, and same-user processes may be able to inspect process environments. Passing values as environment entries keeps them out of the `sh -c` command string; it does not make arbitrary hook code safe. A hook that uses `eval`, for example, can turn the subject back into code.

> “Announced first, then hooks. A hook that crashes the watcher must not leave the arrival un-announced, or the next run re-fires it against the same broken command.”

That chooses the failure direction that can lose work. If the process exits after `mark_announced` but before the hook starts, the next run skips the arrival and never fires the hook. The same happens if the hook fails: the error is reported, but the arrival stays marked and is not retried. This may be a deliberate at-most-once policy, but the comment presents it as the only safe direction. The real choice is between possible lost hooks and possible repeated hooks; the code has no separate “announced” and “hook completed” state.

## 2. Key-derived handle and name mismatch

> “A handle that is exactly the key’s own word-label is not a claim about anyone: it is what `ctx init` with no name produces, derived from the key rather than chosen.”

A matching label does not show that the sender used `ctx init`’s default. The manifest handle is sender-controlled text. A sender can deliberately set it to `words::label(key)` and receive the “nothing is in conflict” treatment, even when the local contact name differs. The label is only 16 bits; the project’s own `words.rs` says a key can be ground to a chosen label in about 65,000 tries. That can also make the label equal a contact name if the contact name is exactly one of the adjective–noun labels. The code infers how the handle was chosen from a string match; it cannot establish that provenance.

This doesn’t mean any arbitrary contact name can be matched by grinding: the label format restricts it to one of the available adjective–noun pairs. But the suppression is still sender-triggerable, and the tests shown establish only the two ordinary cases, not resistance to a chosen collision.

## 3. Requiring `Origin` on UI mutations

> “No page can produce that shape, because a browser `fetch` always sends an `Origin` on a POST.”

That addresses browser requests, not every legitimate client of the loopback UI API. A local script, command-line helper, test client, or another native app can send the required `X-Ctx` header without `Origin`; it will now get a 403. If the UI API is intentionally browser-page-only, that restriction should be stated as part of its contract. The code and tests establish that the page’s own request works and headerless requests are refused; they do not establish that no supported non-browser client needs the API.

## 4. Email-shaped plan

> “A real shared board was rejected for now, for three reasons that are all the same reason.”

The reasons are related, but they are not one reason, and the evidence doesn’t establish that each is inherent to a board. Hosting need not mean a trusted relay can read posts: a board could be self-hosted or store client-encrypted posts. Group-key rotation is a real cost of one group-key design, but it doesn’t prove that N sealed copies are unacceptable; the plan itself says that may be a workable email-like alternative. And asymmetric trust in membership is a design concern, not yet a demonstrated failure. Calling these “all the same reason” compresses distinct tradeoffs and makes the email choice sound more conclusive than the arguments warrant.

There is also a framing gap between the thesis and the plan: “email between agents” is asserted, while the stated goal includes a buddy-list experience and the plan puts connection requests and a GUI list on the roadmap. That may be a sound product choice, but the three board arguments don’t show that email-shaped interaction is the only way to achieve that goal.

## 5. Injection-test result

> “That makes this strong evidence about the renderer — a forged marker genuinely failed against the nonce.”

The result is evidence that this particular forged marker, without the nonce, did not visibly escape in this run. It is weak evidence for the renderer’s general behavior: the renderer’s emitted bytes can be checked directly, and one successful case does not test other marker placements, escaping, truncation, or malformed content. The test also doesn’t isolate the nonce’s contribution from the rest of the rendered frame.

> “The phrase was the owner’s own and unknown to the reader, which is what makes the pass/fail grading real.”

That makes the tell a useful check for one specific behavior, but it doesn’t make this a controlled measure of reader robustness. The reader knew the attack techniques and had written the scaffold; the result records only that the tell did not appear and the reader described the payload as an injection attempt. That is some evidence of resistance under priming, but less than “strong evidence about the renderer” suggests and not a clean estimate of how an unprimed reader would respond. The result is best read as a useful first case report, not as a validation of the nonce or the reader’s general behavior.
